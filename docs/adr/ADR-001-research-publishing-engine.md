# ADR-001: Research and publishing engine

**Status:** Proposed (owner approval needed for the scheduling and LinkedIn parts)
**Date:** 2026-11-25
**Deciders:** Site owner (Pavan Babu Gandla). Technical review: whoever maintains `src/build.py` and the CI workflow.

## Context
The owner wants every valuable research activity to become original content on infiante360techacademy.com, with LinkedIn used to send readers to it. The brief asks for a research hub, 25 research agents, a source registry, daily research, whitepapers, research feeds and LinkedIn derivatives.

Constraints in this repository:
- Static site generated by `src/build.py`, deployed to GitHub Pages by `.github/workflows/pages.yml`. No server or database.
- `src/build.py` runs only in CI. A privacy plugin blocks local runs.
- An agent framework exists (`agents/registry.json`, `agents/orchestrator.py`): 15 deterministic agents work; others are spec-only and report `BLOCKED`.
- Rules in `CLAUDE.md`: no fabricated claims, nothing deploys, posts or sends without the owner's go-ahead, no secrets in Git, no near-duplicate pages.
- LinkedIn prohibits scraping and cookie-based automation, and expects a person to be involved in publishing AI-assisted posts.
- No generative image model or LLM API key is available in CI.

## Decision
Use an **approval-gated, file-based pipeline** that fits the existing build:

1. **Registries are data files** in `data/research/` (`topic_registry.json` exists; add `source_registry.json` and `article_registry.json`). They are the memory: every topic has a status, every source has a URL and a retrieval date recorded by a person or a verified fetch.
2. **Drafting happens in a reviewed session**, not on an unattended schedule. A draft is a Python page module (like `src/content_research.py`) plus a diagram spec. It enters Git on a branch or a commit the owner can review.
3. **Deterministic agents do the checks in CI**: duplicate and cannibalisation check against the route snapshot, link check, source-URL presence, claim-pattern scan (no invented numbers or partner wording), length and metadata limits, JSON-LD validity. These are code, tested, and fail the build.
4. **Publishing is the existing deploy.** Merge to `main` runs build, tests and deploy. Nothing publishes because a schedule fired.
5. **Feeds are generated from published pages only**, extending the current feed writer (`research/rss.xml` first, topic feeds later when each has enough items).
6. **LinkedIn derivatives are draft files** in `marketing/linkedin/research/` with UTM links and status `pending_review`. The owner posts them manually or through LinkedIn's own scheduler. No posting, commenting, connecting or messaging code is written.
7. **Job-market research waits for data.** It uses only the authorised Infinate360Explorer dataset, with methodology, sample size and freshness stated. No public page until that data and a privacy review exist.

## Options considered

### Option A: Fully autonomous daily pipeline (scheduled LLM agents publish directly)
| Dimension | Assessment |
|---|---|
| Complexity | High (secrets, LLM calls, retries, rollbacks) |
| Cost | Ongoing API spend; cost caps needed |
| Scalability | High volume |
| Team familiarity | Low |

**Pros:** Maximum output; no daily effort.
**Cons:** Breaks the no-unreviewed-claims and no-autonomous-publishing rules; needs API keys in CI; high risk of thin or inaccurate pages; conflicts with LinkedIn's human-involvement expectation.

### Option B: Approval-gated file pipeline (chosen)
| Dimension | Assessment |
|---|---|
| Complexity | Low to medium |
| Cost | No new infrastructure |
| Scalability | Quality-bound, tens of articles per month at most |
| Team familiarity | High (same build, tests, CI) |

**Pros:** Reuses everything; every page reviewed; CI enforces the mechanical rules; no new secrets.
**Cons:** Output depends on review capacity; no unattended daily content.

### Option C: Separate CMS or server application
| Dimension | Assessment |
|---|---|
| Complexity | High |
| Cost | Hosting, database, auth, maintenance |
| Scalability | High |
| Team familiarity | Medium |

**Pros:** Editorial UI, scheduling, roles.
**Cons:** Second system of record; the site is static; large effort before any research is published.

## Trade-off analysis
The main trade is volume against trust. The site's value to directors and enterprise buyers rests on accurate, sourced content, and the repository already treats unverified claims as defects. Option B accepts a lower output rate in exchange for checkable quality and no new attack surface. Option C can be reconsidered if review volume becomes the bottleneck and the owner funds a server.

## Consequences
- Easier: adding a topic (registry row, page module, spec); proving what was reviewed (Git history); rollback (revert a commit).
- Harder: unattended daily publishing is not available; the 365-article and 1,095-asset annual targets are not met by schedule alone.
- Revisit: add an LLM-assisted drafting step only with owner-provisioned credentials stored as repository secrets, run on demand, writing drafts to a branch, never to `main`.
- Revisit: a research feed per topic once each has at least a handful of published items.
